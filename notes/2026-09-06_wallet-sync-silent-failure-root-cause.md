# Wallet sync: 30 consecutive failed runs reported as "success"

**Date**: 2026-09-06
**Trigger**: The new wallet dashboard showed every recent run red while
`last-sync.json` read `"last_run_status": "success"`.

## Objective

Find why `wallet-sync-unified` had been failing hourly since 2026-09-05, and why
nothing recorded it.

## Approach

Read the newest log, reproduced the failing subprocess directly, then bisected
the format registry it loads.

## Inputs

- `~/automation-monorepo-config/data/expense-domain/wallet/logs/*.log` (58 runs, 30 failed)
- `~/automation-monorepo-config/data/expense-domain/wallet/last-sync.json`
- `~/automation-monorepo-config/config/expense-domain/gmail/email-formats/*.yaml` (18 files)

## Steps & findings

1. The log ends at `subprocess.CalledProcessError … extract-engine.py --ai-assist
   returned non-zero exit status 1` — the command, never the reason.
   `run_engine()` called `subprocess.run(..., capture_output=True, check=True)`,
   so the engine's stderr was captured into the exception and discarded.

2. Ran the engine by hand on a synthetic envelope. It failed **with and without**
   `--ai-assist` — the flag was a red herring. Real error:

   ```
   yaml.scanner.ScannerError: mapping values are not allowed here
     in email.hdfc-autopay-cancellation.yaml, line 9, column 16
   ```

3. Line 9 is `  subject: View:`. A bare YAML scalar cannot contain `: ` — the
   parser reads `View:` as a second mapping key. Scanning all 18 format files
   found **4 broken, all with the same `subject: View:`**, all carrying the
   header `# Generated by AI pattern suggestion`.

4. `create_format_file_from_suggestion()` built the file with an f-string:

   ```python
   subject: {subject.split()[0] if subject else 'transaction'}
   ```

   The HDFC alert subjects begin with the literal token `View:`, so the
   generator emitted invalid YAML. It also used the token unescaped as a regex.

5. `load_formats()` iterated every file with no error handling, so **one** bad
   file aborted the whole registry — and therefore every sync run, permanently.
   The four bad files were written 2026-09-05; the failures start there.

6. `main()` called `save_state()` only on the final success path. A crash
   anywhere left `last-sync.json` byte-identical to the last good run. The
   schema on disk (`last_run_start`, `last_run_end`, `last_run_summary`) was
   also stale: the running code wrote none of those keys, only a sentence in
   `last_run_status`.

## Results

Four defects, one visible symptom:

| # | Defect | Fix |
|---|---|---|
| 1 | Generator emits YAML by string interpolation | Build a dict, `yaml.safe_dump` it, `re.escape` the subject, then parse it back and `_validate` before writing |
| 2 | One bad format file aborts every run | Skip and warn per file; `strict=True` for `--test` / `--check-formats`; still raise if *nothing* usable remains |
| 3 | Engine stderr discarded on failure | Check the return code and raise with the captured stderr; log engine warnings on success |
| 4 | State written only on success | Stamp `running` at start, `failed` + `last_run_error` on any `BaseException`, `success` with a real summary at the end; `flush()` the log in a `finally` |

Plus: `last_run_summary` counted `failed: 0` unconditionally. It now carries the
real per-document tallies from Part A.

## Interpretation

The AI-suggestion feature was self-poisoning: it wrote a file that disabled the
pipeline that writes files. The blast radius came from defect 2 (no isolation)
and the invisibility from defects 3 and 4. Fixing only the four YAML files would
have restored service and left the trap armed.

Post-fix dry run: 19 documents fetched, 5 extracted and ready to push, 10 not
extracted, 1 unrouted, 3 skipped by rule. Exit 0.

## Caveats

- The four repaired files are in `~/automation-monorepo-config/`, outside this
  repo. Backup of all 18 originals: `/tmp/fmt-backup/` (transient).
- **10 documents still do not extract.** They now load and match
  `hdfc-autopay-cancellation`, but its AI-written body regex is too rigid
  (`field regex 'body' did not match`). Separate work: the patterns are wrong,
  not broken.
- `last_run_summary` counts Part A only; Part B (Drive) is skipped in dry-run
  and contributes just its pushed count.
- Not verified against a live (non-dry) run — that would push 5 records into the
  real Wallet account.
